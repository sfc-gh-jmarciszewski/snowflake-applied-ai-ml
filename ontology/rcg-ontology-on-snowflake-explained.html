Ontology on Snowflake for Retail & Consumer Goods

How a pair of tables, some metadata, and an agent let you ask a database about suppliers and channels instead of rows and columns.

Databases are very good at remembering facts and very bad at knowing what those facts mean. A table called SUPPLY_AGREEMENTS knows that vendor 1 has a row pointing at retailer 1 with a start and end date. It does not know that a manufacturer is a kind of supplier, that a distribution contract is another route into the same shelf, or that a distributor serving a retailer is, in the sense that matters to most category, sourcing and supplier-risk questions, also selling into that retailer.

Ontology on Snowflake is an open-source reference implementation from Snowflake Labs that bolts that meaning onto the data, natively, using nothing but tables, views, a stored procedure, three semantic models and a Cortex Agent. The repository ships with a sports sample; in this article we apply the same pattern to a retail and consumer goods (RCG) supply network, build it up one layer at a time, and then follow a single question through the whole machine, from the moment it's typed to the moment an answer comes back.

Throughout, we'll use a small, fictional network of manufacturers, distributors, retailers and promotions. Every company is invented and every agreement date is illustrative. The core objects — KG_NODE, KG_EDGE, the ONT_* metadata tables, REL_RESOLVED and the view generator — are the repository's; the RCG classes, view names, semantic-model files and tool names are this article's adaptation.

Nodes and edges

Everything starts with two tables. KG_NODE holds every thing: one row per entity, with an ID, a type, a name and a VARIANT column called PROPS where type-specific attributes live as JSON — a retailer's format and store count, a manufacturer's category. KG_EDGE holds every connection: a source ID, a destination ID, an edge type, a weight, its own PROPS (SKU count, annual value), and a pair of dates that say when the connection was true.

That's the entire physical model. There is no VENDORS table and no STORES table. A new kind of entity — a broker, a co-packer, an e-commerce marketplace — is a new value in NODE_TYPE, not a migration. Hover over a row, or over a circle, to see how the same data reads as a table and as a graph:

Notice the NODE_ID values. The repository's loader (09_load_data.sql) simply casts source keys to strings, so if you load a vendor master and a retailer master the same way, retailer 1 (FreshMart) and manufacturer 1 (Alpine Beverages) share an ID. It works because nothing ever looks at KG_NODE raw: every query goes through a view filtered by NODE_TYPE, which is our first hint that the views matter more than the tables. (In production you'd more likely key on GLN or an MDM ID.)

Time

Edges aren't just connections; they're connections during an interval. Every supply or distribution agreement is an edge with EFFECTIVE_START and EFFECTIVE_END, and a NULL end means "still in force". Any question with "currently", "in 2015" or "on 1 January 2025" in it — "who was on the approved vendor list when the recall hit?" — becomes a simple range predicate on these two columns. We'll lean on that heavily later.

Classes

So far we have a graph, but not an ontology. The graph knows that node 101 has type DISTRIBUTOR; it doesn't know what a distributor is. Layer 2 adds that knowledge as rows in a set of metadata tables. The most important is ONT_CLASS, which arranges types into a hierarchy. This is the whole trick behind polymorphic queries. A question about Suppliers doesn't care whether the answer is a Manufacturer shipping direct or a Distributor shipping from its own DC; it just wants everything underneath. The same idea applies to relationships. ONT_RELATION_DEF declares concrete links like SUPPLIES (Manufacturer → Retailer) and SERVES (Distributor → Retailer), and an abstract one, sells_into, from Supplier to Channel. The metadata layer goes further than this: ONT_PROPERTY types each attribute, ONT_RULE holds inference rules (for example, sources_from is the inverse of sells_into), there are interfaces like Named and Temporal, action types such as Onboard Supplier or Delist Item, and ONT_PERMISSION maps ontology roles like category manager and analyst to object and link types. All of it is ordinary rows in ordinary tables, which means the ontology can be queried like any other data.

Generated views

Metadata on its own doesn't answer anything. Layer 3 turns it into something SQL can use. A Python stored procedure, SP_GENERATE_ONTOLOGY_VIEWS(), reads two mapping tables — ONT_CLASS_MAP for classes and ONT_REL_MAP for relationships — and, for each abstract class or relation, writes a UNION ALL view over its concrete implementations. Step through what it does:

The result is a stack of views. At the bottom are type views like V_MANUFACTURER that just filter KG_NODE and pull fields out of PROPS. Above them sit relationship views like V_SUPPLIES, a unified REL_RESOLVED view over every edge, and finally the abstract views: VW_ONT_SUPPLIER, VW_ONT_CHANNEL, VW_ONT_EVENT, VW_ONT_SELLS_INTO, VW_ONT_PARTICIPATES_IN. Because they're views, they cost nothing until queried and never go stale.

Five layers

We now have the three data layers. Two more sit on top, and they're where natural language enters the picture. Layer 4 is a set of Cortex Analyst semantic models — YAML files that describe tables, columns, joins and synonyms ("vendor", "supplier", "brand owner") so an LLM can write SQL against them. Layer 5 is a Cortex Agent that decides which model, or which graph algorithm, a question needs. Pull the stack apart to see each layer:

The three semantic models split the work by the kind of question. The Knowledge Graph model covers concrete views (V_MANUFACTURER, V_SUPPLIES, …) and is fast and precise for "which manufacturers supply X". The Ontology model covers the abstract views and is what you need for "who sells into X", direct and indirect. The Metadata & Governance model points at the ONT_* tables themselves so the agent can answer questions about the ontology, like "what object types exist?" or "what can the category-manager role see?".

Paths

Not every question is a filter. "How is Alpine Beverages connected to Brightside Snacks?" — a shared retailer, a shared distributor, a common exposure if one of them has a disruption — has no natural SQL shape, which is why the agent hands such questions to the graph tools. Those run in a Snowpark Container Services service that loads the graph into NetworkX and runs real graph algorithms: shortest paths, centrality (which supplier is a single point of failure?), Louvain communities, supplier-switching and temporal analysis. Putting it together

Step back and the design is surprisingly modest. Two tables hold the facts. A handful of metadata tables hold the meaning. A stored procedure compiles meaning into views. Semantic models translate views into vocabulary an LLM can use, and an agent picks the right vocabulary for each question. Every layer is a standard Snowflake object, so governance, access control and cost all work the way they already do.

The payoff is that the hard part — deciding that a distributor is a supplier, that serving a retailer is a way of selling into it, that "selling into" should include both direct and indirect routes — is written down once, as data, rather than re-derived in every supplier scorecard, category review deck and prompt. The question we followed had no idea that Atlas Distribution lived in a different table from Alpine Beverages. It didn't need to.
