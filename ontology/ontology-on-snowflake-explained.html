Ontology on Snowflake

How a pair of tables, some metadata, and an agent let you ask a database about people and organizations instead of rows and columns.

Databases are very good at remembering facts and very bad at knowing what those facts mean. A table called PLAYER_CONTRACTS knows that person 1 has a row pointing at club 1 with a start and end date. It does not know that a player is a kind of person, that a contract is a kind of employment, or that a coach on the same club's payroll is, in the sense that matters to most questions, a colleague of that player.

Ontology on Snowflake is an open-source reference implementation from Snowflake Labs that bolts that meaning onto the data, natively, using nothing but tables, views, a stored procedure, three semantic models and a Cortex Agent. In this article we'll build it up one layer at a time and then follow a single question through the whole machine, from the moment it's typed to the moment an answer comes back.

Throughout, we'll use the repository's own sample data: a small, synthetic world of soccer players, coaches, clubs and matches. The names are real; the careers are partly invented, so don't be alarmed when you see an unexpected transfer.

Nodes and edges

Everything starts with two tables. KG_NODE holds every thing: one row per entity, with an ID, a type, a name and a VARIANT column called PROPS where type-specific attributes live as JSON. KG_EDGE holds every connection: a source ID, a destination ID, an edge type, a weight, its own PROPS, and a pair of dates that say when the connection was true.

That's the entire physical model. There is no PLAYERS table and no CLUBS table. A new kind of entity is a new value in NODE_TYPE, not a migration. Hover over a row, or over a circle, to see how the same data reads as a table and as a graph:

Notice the NODE_ID values. The loader in 09_load_data.sql simply casts the source keys to strings, so club 1 (Real Madrid) and person 1 (Mbappé) share an ID. It works because nothing ever looks at KG_NODE raw: every query goes through a view filtered by NODE_TYPE, which is our first hint that the views matter more than the tables.

Time

Edges aren't just connections; they're connections during an interval. Every contract is an edge with EFFECTIVE_START and EFFECTIVE_END, and a NULL end means "still true". This turns the graph into something closer to a film than a photograph. Drag the slider to scrub through it:

Any question with "currently", "in 2015" or "on 1 January 2025" in it becomes a simple range predicate on these two columns. We'll lean on that heavily later.

Classes

So far we have a graph, but not an ontology. The graph knows that node 101 has type COACH; it doesn't know what a coach is. Layer 2 adds that knowledge as rows in a set of metadata tables. The most important is ONT_CLASS, which arranges types into a hierarchy. Four classes are abstract — they never appear in NODE_TYPE — and four are concrete:

This is the whole trick behind polymorphic queries. A question about Person doesn't care whether the answer is a Player or a Coach; it just wants everything underneath. The same idea applies to relationships. ONT_RELATION_DEF declares concrete links like PLAYS_FOR (Player → Club) and COACHES (Coach → Club), and an abstract one, works_for, from Person to Organization. The metadata layer goes further than this: ONT_PROPERTY types each attribute, ONT_RULE holds inference rules (for example, employs is the inverse of works_for), there are interfaces like Named and Temporal, action types such as Transfer Player, and ONT_PERMISSION maps ontology roles like viewer and analyst to object and link types. All of it is ordinary rows in ordinary tables, which means the ontology can be queried like any other data.

Generated views

Metadata on its own doesn't answer anything. Layer 3 turns it into something SQL can use. A Python stored procedure, SP_GENERATE_ONTOLOGY_VIEWS(), reads two mapping tables — ONT_CLASS_MAP for classes and ONT_REL_MAP for relationships — and, for each abstract class or relation, writes a UNION ALL view over its concrete implementations. Step through what it does:

The result is a stack of views. At the bottom are type views like V_PLAYER that just filter KG_NODE and pull fields out of PROPS. Above them sit relationship views like V_PLAYS_FOR, a unified REL_RESOLVED view over every edge, and finally the abstract views: VW_ONT_PERSON, VW_ONT_ORGANIZATION, VW_ONT_EVENT, VW_ONT_WORKS_FOR, VW_ONT_PARTICIPATES_IN. Because they're views, they cost nothing until queried and never go stale.

Five layers

We now have the three data layers. Two more sit on top, and they're where natural language enters the picture. Layer 4 is a set of Cortex Analyst semantic models — YAML files that describe tables, columns, joins and synonyms so an LLM can write SQL against them. Layer 5 is a Cortex Agent that decides which model, or which graph algorithm, a question needs. Pull the stack apart to see each layer:

The three semantic models split the work by the kind of question. The Knowledge Graph model covers concrete views (V_PLAYER, V_PLAYS_FOR, …) and is fast and precise for "who plays for X". The Ontology model covers the abstract views and is what you need for "who works for X". The Metadata & Governance model points at the ONT_* tables themselves so the agent can answer questions about the ontology, like "what object types exist?" or "what can the analyst role do?".

Not every question is a filter. "How is Mbappé connected to Haaland?" has no natural SQL shape, which is why the agent hands such questions to the graph tools. Putting it together

Step back and the design is surprisingly modest. Two tables hold the facts. A handful of metadata tables hold the meaning. A stored procedure compiles meaning into views. Semantic models translate views into vocabulary an LLM can use, and an agent picks the right vocabulary for each question. Every layer is a standard Snowflake object, so governance, access control and cost all work the way they already do.

The payoff is that the hard part — deciding that a coach is a person, that coaching is a kind of working, that "working for" should include both — is written down once, as data, rather than re-derived in every query, dashboard and prompt. The question we followed had no idea that Ancelotti lived in a different table from Mbappé. It didn't need to.
